# Видение проекта

## Общее описание

Nullae — это система автоматического обнаружения и инвентаризации инфраструктуры, позволяющая отслеживать и связывать сетевые сущности (Domain, Node, Ip) в едином реестре.

## Технический стек

- **Язык программирования**: Rust
- **Веб-компоненты**: WebAssembly (WASM)
- **Фреймворк**: Yew
- **CSS фреймворк**: Tailwind CSS
- **Архитектура**: Компонентный подход
- **Запуск и тестирование**: Trunk

## Принципы разработки

### KISS (Keep It Simple, Stupid)

- Простые и понятные решения без излишней сложности
- Минимум абстракций, максимум ясности кода
- Избегание преждевременной оптимизации

### MVP (Minimum Viable Product)

- Приоритет базовой функциональности над дополнительными возможностями
- Быстрая доставка рабочего продукта пользователям
- Валидация идей на минимальной реализации

### Конфигурация через переменные окружения

- Все настройки приложения через environment variables
- Отсутствие хардкода конфигурационных значений
- Простота развертывания в разных средах

### Fail Fast

- Быстрое обнаружение и сообщение об ошибках

- Короткие циклы разработки с регулярными релизами
- Непрерывная обратная связь от пользователей
- Постепенное улучшение и расширение функциональности

## Работа с сущностями

- **Иерархия:** Сущности могут иметь дочерние элементы через поле `children` (список хэшей).
- **Связывание:** Для добавления дочерней сущности используйте метод `entity.add_child(hash)`.
- **Пример:** `Domain -> Node -> Ip`. При создании `Node`, она добавляется как child к `Domain`. При обнаружении IP, он добавляется как child к `Node`.
- **Удаление:** При удалении сущности, необходимо проверить наличие детей (`has_children()`) и запретить удаление, если они есть, либо реализовать каскадное удаление.

## Ключевые архитектурные концепции

### 1. Основные модули и их взаимодействие

Система состоит из следующих логических компонентов:
- **`nullae-core`**: Центральная библиотека, содержащая бизнес-логику, модели данных (сущности) и механизмы взаимодействия с базой данных (Consul). Предоставляет прелюдии, общие структуры хранилища и обработчики (handlers).
- **`nullae` (CLI)**: CLI-интерфейс, который парсит аргументы командной строки с помощью `clap` и вызывает соответствующие хэндлеры из `nullae-core` (`discovery`, `list`, `delete`, `show`).
- **`nullae-api`**: REST-сервер на базе фреймворка `axum`. Предоставляет HTTP API для создания (`/api/v1/short`) и разрешения (`/{short_url}`) коротких ссылок.
- **`nullae-ui`**: Легковесное frontend-приложение на WebAssembly (WASM) с использованием `Yew` и `Tailwind CSS`. Общается с `nullae-api` по HTTP.

```
Схема взаимодействия модулей:
CLI (nullae) ────┐
                 ├─> nullae-core ──> Consul KV (Хранилище & Индексы)
Web UI (nullae-ui) ─> nullae-api ──┘
```

### 2. Ключевые структуры данных и их назначение

- **`HashID`**: Типобезопасная обертка вокруг 32-байтового массива SHA-256 хэша. Обеспечивает строгий контроль уникальности сущностей на основе их ключевых свойств.
- **`Metadata`**: Служебные метаданные сущности, содержащие время создания (`created_at`), обновления (`updated_at`) и опциональный список идентификаторов дочерних элементов (`children: Option<Vec<HashID>>`).
- **`Entity`**: Универсальный контейнер, объединяющий `Metadata` и `EntityKind` (через `#[serde(flatten)]`). Обеспечивает единый интерфейс сериализации и хранения в Consul.
- **`EntityKind`**: Перечисление видов сущностей:
  - `Domain`: Доменное имя инфраструктуры (родитель для `Node`).
  - `Node`: Вычислительный узел (сервер), содержащий сведения об ОС, оборудовании и сетях.
  - `Ip`: Сетевой адрес узла (привязывается к интерфейсу `Node`).
  - `Url`: Ссылка, используемая для сокращения (содержит slug и исходный URL).
- **`Context<S>`**: Контекст приложения, владеющий хранилищем `S: Storage`. Передается через все уровни приложения для инъекции зависимостей.
- **`Index` и `Item`**: Структуры для реализации инвертированных индексов. Позволяют быстро находить сущности по полям (например, `hostname`, `name`, `slug`), не прибегая к полному сканированию Consul.

### 3. Механизмы обработки ошибок и логирования

- **Обработка ошибок**:
  - Строго запрещено использовать `unwrap()` и `expect()` в рабочем коде (за исключением тестов).
  - Все потенциальные сбои возвращают тип `anyhow::Result<T>`.
  - Для создания и форматирования ошибок используются макросы `anyhow!` и `bail!`.
  - При пробросе ошибок вверх по стеку обязательно добавляется понятный контекст через метод `.context("...")`.
  - Кастомный `error::Error` enum используется только в крайних случаях для специфической логики и не должен расширяться ad-hoc.
- **Логирование**:
  - Реализовано с помощью библиотеки `tracing`.
  - Уровни логов: `error!` для критических ошибок, `warn!` для unexpected-сценариев, `info!` для ключевых событий жизненного цикла, `debug!` для отладки.
  - Настройка фильтрации логов вынесена в переменную окружения `RUST_LOG` через `EnvFilter`.

### 4. Принципы работы с API и внешними сервисами

- **Consul KV**:
  - Используется как распределенное хранилище сущностей и индексов.
  - Все сущности сериализуются в JSON и сохраняются по путям вида `0ae/entity/<hash>`.
  - Инвертированные индексы сохраняются по путям вида `0ae/index/<index_field>/<value>` и содержат списки `HashID` ассоциированных сущностей.
  - Взаимодействие происходит асинхронно через HTTP клиент `reqwest` с настроенным пулом соединений (TCP keep-alive).
- **REST API (Backend)**:
  - Реализовано на `axum`. Эндпоинты разделены по методам (POST для мутаций, GET для чтения).
  - Обработка ошибок в роутах не отдает подробности ошибок во внешний мир, возвращая стандартные HTTP статусы.
- **WASM Client (Frontend)**:
  - Неблокирующий асинхронный HTTP клиент построен на `gloo::net::http::Request`.
  - Все вызовы используют `wasm-bindgen-futures::spawn_local` для запуска футур в JS event loop.
